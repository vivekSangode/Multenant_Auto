## 1. Target rule (owner)

Platform → Company → Company users. `CMP_<n>` is the only company identifier; company terminology everywhere. No new code introduces `ORG_<n>`, `org_<n>`, `org-*`, `organization_id` or `organizationCode` (outside isolated data-migration tooling). Legacy code may remain only temporarily, explicitly identified, with a removal plan, unused by the company runtime, never creating ORG_* resources, never used by new tests.

**Stage D — what changed (2026-10-05, API-GATEWAY only; backup of `src` + `pom.xml` before the change in the agent scratchpad `backup-stage-d/`):**

- **Removed / replaced (owner approval 2026-10-05):** `filter/OrganizationContextFilter` → `filter/CompanyContextFilter`, `filter/OrganizationSelection` → `filter/CompanySelection`, tests `OrganizationContextFilterTest` → `CompanyContextFilterTest`, `OrganizationSelectionTest` → `CompanySelectionTest`. `OrganizationContextFilter` (`A +`, scheduled add) and `OrganizationContextFilterTest` (`M +`) via `svn rm --force` (local working copy only); the two others were unversioned.
- **Company resolution (`CompanySelection.fromToken`):** the company is the verified token's `tenant_id` claim and nothing else — a single string matching COMMON `TenantResourceNaming.isCompanyCode` (`^CMP_[0-9]{1,8}$`). Missing, empty, non-string, list, malformed, lowercase or retired `ORG_` values → 403. The `groups` claim and the `Active-Org` header are no longer read; no request header, query parameter or Keycloak group can select or override the company. The token itself is verified by the existing resource-server configuration (staff realm / customer realm issuer, signature, expiry, audience; customer tokens only on `/portal/**`) — unchanged.
- **`CompanyContextFilter`:** strips the client trust headers (`X-Company-Code`, `X-Organization-Id`, `Active-Org`, `X-Tenant-Id`, `X-Performed-By(-Id)`, customer identity headers; `X-User-Token` re-derived); public / docs / actuator paths pass without a company; other paths need a verified JWT (401); Control Panel platform-admin routes (`/control-panel/api/v1/platform/**`) carry no company (unchanged); every other route needs a valid `tenant_id` (403), then the module entitlement `COMPANY_MODULES:<companyCode>` (Redis set published by the CP for ACTIVE companies only; missing / empty answer → 403, Redis error → 503; CONTROL-PANEL and NOTIFICATION skip only the plan check, as before); forwards `X-Company-Code` = the token's company, the verified user and the token.
- **WebSocket tickets:** `WebSocketTicketBinding.companyCode`; `POST /ws-ticket` binds the token's `tenant_id` company (the `Active-Org` parameter is gone); on redemption the ticket company travels as the exchange attribute `erp.websocket.ticket-company` (no header) and `CompanyContextFilter` refuses a token of another company (403) or another user (401).
- **Rate limiter:** key `TENANT:<companyCode>:USER:<user>` from the verified token's `tenant_id` (not from a header).
- **Contract:** `CompanyContextFilter.COMPANY_CODE_HEADER` = COMMON `TenantContextFilter.COMPANY_CODE_HEADER` (`X-Company-Code`), `COMPANY_MODULES_PREFIX` = COMMON `ModuleEntitlementEnforcementFilter.KEY_PREFIX` = CP publisher key (asserted by a test). The CP is unchanged.
- **Not in stage D:** the issuer → company equality against the realm registry and the per-company realm (`co-<n>`) with its hard-coded `tenant_id` mapper (stage F / P03-T5); a company-status check at the gateway (`TENANT_STATUS`, P06-T6 — today the services refuse non-ACTIVE companies through the metadata resolver, and `COMPANY_MODULES` exists only for ACTIVE companies); developer guide §8 still quotes the old header names (stage G).
- **Operational note:** until stage F, the existing staff and customer development realms must emit a `tenant_id` claim (`CMP_<n>`) through a protocol mapper, otherwise every tenant route answers 403 (fail closed). No realm configuration is stored in this repository (only a CP test resource), so nothing was changed there.
