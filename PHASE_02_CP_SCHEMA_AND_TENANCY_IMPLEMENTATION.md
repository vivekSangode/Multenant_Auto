## 1. Objective

Implement the data foundation designed and approved in PHASE_01:

1. A **Company** entity that replaces the Customer + Organization pair in the control plane. It keeps the technical company code `CMP_<n>`.
2. The new Company-based control-plane **entities**. **CD-27 (owner decision):** during development the CP schema stays generated by Hibernate `ddl-auto: update` from these entities; **no CP Liquibase is written in this phase**. The clean CP Liquibase baseline and `ddl-auto: validate` come in [PHASE_11A](PHASE_11A_FINAL_CP_LIQUIBASE_BASELINE.md), after the CP model is stable.
3. A race-safe **id sequence** for `CMP_<n>` (the single company identifier, CD-26).
4. A **company resource registry** (`tbl_company_resource`) that replaces `tbl_organization_database` as the routing source and reserves every resource name.
5. **Database credentials stay environment-level** (CD-03): the existing `EnvironmentTenantCredentialProvider` is kept; no per-company DB users or credential tables. The **realm registry** table `tbl_identity_realm` (CD-06) is created here; its logic comes in PHASE_03.
6. **Liquibase-based tenant schema management** in COMMON-LIBRARY, replacing the Hibernate `update` bootstrap, including the bootstrap modes `SEEDED`, `EMPTY_FOR_IMPORT` (the standard option for companies onboarded with existing data, e.g. Shivam) and `UPGRADE`.
7. Backward-compatible internal tenant metadata, so that the domain services keep working unchanged.

## 6. New development required

### 6.1 Company model (control plane)

- **Entities:** `Company`, `CompanyProfile`, `CompanySetting`, `CompanyResource` (DATABASE and BUCKET rows per company and purchased module, IDP_REALM), `CompanyStatusHistory`, `IdSequence`, `IdentityRealm`.
- **`CompanyStatus` enum:** `DRAFT`, `PROVISIONING`, `PROVISIONING_FAILED`, `AWAITING_DATA_IMPORT`, `ACTIVE`, `SUSPENDED`, `DISABLED`, `ARCHIVED`, `PURGE_APPROVED` (PHASE_01 §6.2 A, master §7.1); plus `onboarding_type` NEW / IMPORT_EXISTING_DATA.
- **`CompanyService`:** create (allocate codes, validate input, reserve the slug), read, update the profile, and change lifecycle with transition rules. The lifecycle endpoints are wired in PHASE_04 together with platform permissions.
- **`CompanyCodeAllocator`:** allocates from `tbl_id_sequence` under `SELECT … FOR UPDATE` in a `REQUIRES_NEW` transaction. Returns `CMP_<n>`. (LEGACY: today `CompanyOrganizationService` returns `"ORG_" + n`; replaced.)
- **Company Login Code** (CD-15): `tbl_company.login_code` (unique, `^[A-Z0-9]{6,12}$`, chosen or generated by the platform, not derived from the company code, the realm or a DB name; changed only by an audited platform operation). It is used only by the login discovery API (PHASE_03).
- **`SlugPolicy`:** the regex `^[a-z0-9](?:[a-z0-9-]{1,38}[a-z0-9])$`, a reserved-word list (`admin`, `api`, `platform`, `www`, `internal`, `control-panel`, every module code), uniqueness, and a suggestion from the display name. **The name is never used for any resource.**
- **`CompanyResourceRegistry`:**
  - `reserve(company, type, module, name)` inserts a RESERVED row; the unique constraint protects against collisions;
  - `markCreated`, `markVerified`, `markOrphaned`;
  - `findDatabase(companyCode, serviceName)` serves the metadata API.

### 6.2 Internal tenant metadata (compatible)

- Serve `GET /api/v1/internal/platform/companies/{companyCode}/metadata?serviceName=` with the `TenantMetadata` payload: `companyCode` = company code (path and field renamed from `/organizations/{id}` / `organizationId` in P02-T11 stage B, 2026-10-05; COMMON `ControlPlaneClient` changed with it), `status` mapped to the existing values so `TenantMetadataResolver.validateStatus` keeps working.
- Status mapping:

  | Company status | Returned status |
  |---|---|
  | ACTIVE | ACTIVE |
  | PROVISIONING (and an ADD_MODULE job for that module) | PROVISIONING |
  | SUSPENDED, DISABLED, ARCHIVED, DRAFT, PROVISIONING_FAILED | SUSPENDED or DISABLED (both deny) |

- `dbName`, `dbHost` and `dbPort` come from the VERIFIED `DATABASE` resource row for (company, module of `serviceName`). If no row exists, return 404, which the resolver turns into 403.
- Serve `GET /api/v1/internal/platform/companies/active` (renamed from `/organizations/active` in P02-T11 stage B). It returns the company codes (`CMP_<n>`) of ACTIVE companies. A module filter parameter `?module=` is added for PHASE_03.

### 6.3 Database credentials and realm registry (corrected 2026-10-03)

- **CD-03:** the infrastructure DB credentials stay in the environment, and the existing `EnvironmentTenantCredentialProvider` is unchanged.
  - The runtime account is least-privilege: only the `cmp\_%` schemas and the CP DB, no MySQL admin rights. This is set up by the owner or operator.
  - The company database is chosen only through the registry. There is no credential table, no credential API, no per-company DB user and no `ControlPlaneTenantCredentialProvider`; the v2–v4 credential model is withdrawn.
- **Secret-reference mechanism** (`CredentialCipher`, AES-256-GCM, master key from the environment): it is built **only when first needed** by PHASE_13 (OAuth tokens) or PHASE_14 (gateway keys). It is not part of R1.
- **Realm registry:** `tbl_identity_realm` (PHASE_01 §6.5.2) + `tbl_identity.identity_realm_id` are added in this phase as JPA entities (schema by Hibernate during development, CD-27). The internal API `GET /api/v1/internal/platform/identity-realms` (the issuer allow-list) comes in PHASE_03.

### 6.4 Tenant schema migration (COMMON-LIBRARY)

> Scope note (CD-27): the owner decision to defer Liquibase applies to the **Control Plane DB only**. Company (tenant) databases keep the Liquibase design below (AD-09, master §16.5).

- `LiquibaseTenantSchemaMigrator`:
  1. connects to the target database as the DDL account;
  2. takes the existing MySQL named lock;
  3. runs the service's `classpath:db/changelog/db.changelog-master.xml` with `liquibase.update` and the context `tenant`;
  4. then runs Hibernate `validate` with the runtime naming strategies;
  5. then runs the seeders, unless the mode is `EMPTY_FOR_IMPORT`;
  6. records the result.
- The bootstrap endpoint gains a request body `{ "mode": "SEEDED" | "EMPTY_FOR_IMPORT" | "UPGRADE" }`. The default is SEEDED, so existing callers that send no body keep today's behaviour.
  - SEEDED: create the schema, then run the seeders. This is the standard mode for a new company.
  - EMPTY_FOR_IMPORT: create the schema, skip the seeders. This is the standard option for companies onboarded with existing data (PHASE_01 §6.8).
  - UPGRADE: migrate only (used by `SCHEMA_UPGRADE` jobs).
- The response reports the applied changeset count, the latest changeset id and the validation result.
- The **populated-database guard stays**: in SEEDED mode, a database with rows that has no `DATABASECHANGELOG` is refused (`409 TENANT_DB_NOT_EMPTY`).
- Changelog prerequisites per service: the master must be runnable on an **empty** database and produce exactly the entity schema. The 2026-10-02 parity work is the basis. A parity test per service compares the Liquibase-created schema with the Hibernate metamodel (re-using the information-schema diff approach of that work).
- ACCOUNT-BOOK: its own bootstrap controller is aligned with the common migrator. It needs `allowMultiQueries=true` (`LIQUIBASE_CONVENTIONS.md`).
- COMPLIANCE: the Camunda `ACT_*` contributor runs after Liquibase, unchanged.

### 6.5 Naming extensions

## 8. Proposed schema changes

**Schema mechanism (CD-27, owner decision 2026-10-03):** the CP schema is generated by Hibernate `ddl-auto: update` from the JPA entities during development. This phase writes **no** CP Liquibase changelog (no baseline, no seed changeset, no temporary or `legacy` changelog layer) and creates no table or FK only to satisfy Liquibase. The clean baseline is PHASE_11A.

Entities added or changed in `control_panel_db` (target columns in PHASE_01 §6.2, groups A, B, F, H, mapped in JPA):
- New: `tbl_company`, `tbl_company_profile`, `tbl_company_setting`, `tbl_company_resource`, `tbl_company_status_history`, `tbl_id_sequence`, `tbl_identity_realm`.
- Changed: `tbl_identity` (realm FK, scope), `tbl_identity_sync_task` (`company_code`), and, where PHASE_02 code needs them, `tbl_platform_audit_log` / `tbl_provisioning_job` / `tbl_provisioning_step` (their full target columns are delivered by PHASE_04 / PHASE_08).
- Replaced by the Company model in this phase: `tbl_customer`, `tbl_organization`, `tbl_organization_database` (entities removed after their callers are migrated). Legacy entities whose replacement belongs to a later phase (membership, subscription, plan, application catalog) **stay as they are** and are only re-pointed from customer/organization to company where they reference them; each later phase replaces its own legacy entities. No duplicate target table is created early only because a later phase owns the concept.
- **Approach:** a fresh development `control_panel_db` is generated from the new entities. The existing development database is backed up and kept until the owner approves dropping it (no automatic drop). Tables left behind by removed entities in an existing development database are harmless and are not dropped by this phase.
- The entity mappings declare every FK, unique key and index of PHASE_01 §6.2 (fixing the missing FKs of the old model). The final constraint names (`uk_`, `fk_`, `idx_`, `ck_`), database CHECK constraints and seed data are delivered by the PHASE_11A baseline.

**Tenant databases:** no structural change. Each gains a `DATABASECHANGELOG` / `DATABASECHANGELOGLOCK` when it is migrated with Liquibase.

## 11. Security and tenant-isolation requirements

1. Resource names come only from `company_code`. Unit tests prove that no API input reaches a name.
2. The environment DB credentials are never stored in the CP DB, logs or APIs. The runtime account is least-privilege (CD-03 compensating controls, PHASE_01 §6.1.4).
3. Secrets in `.env` files are owner-managed and rotated where they were exposed (Q-22).
4. The bootstrap verifies that the derived database name equals the VERIFIED registry row before migrating. A mismatch returns 409.
5. The Liquibase runner never runs `dropAll` or any `drop*` change. A build-time check rejects `<dropTable>` / `<dropColumn>` in tenant changelogs unless they are listed with explicit owner approval in a reviewed allow-list (expand–contract).

## 13. Acceptance criteria

1. The control plane starts on an empty development `control_panel_db` with `ddl-auto: update`, and the generated Company-model tables match PHASE_01 §6.2 A, B, F, H (columns, types, lengths, nullability, unique keys, indexes, FKs; checked by a schema IT). (The Liquibase start and `ddl-auto: validate` are acceptance criteria of PHASE_11A, CD-27.)
2. Creating 50 companies concurrently yields 50 unique, gap-tolerant `CMP_<n>` codes with no duplicates (concurrency IT).
3. The metadata API returns the same payload shape as before for an ACTIVE company. The resolver tests pass unchanged.
4. Domain services connect to company databases with the environment credentials and the registry DB name only. No request input can change the database (test).
5. Bootstrap in SEEDED mode on an empty database creates the schema through Liquibase, validates and seeds. Running it again is a no-op.
6. Bootstrap in EMPTY_FOR_IMPORT mode creates the schema and skips the seeders.
7. The parity tests pass for every tenant module.
8. No resource name in any test derives from a company name or slug.

## 15. Risks and rollback considerations

| Risk | Mitigation |
|---|---|
| Changelog/entity drift makes tenant migration fail | Parity tests per service (task 7); validate after migrate |
| Breaking the domain services' metadata contract | Compatible payload; the resolver tests are unchanged |
| Losing the development control-plane data | It is development data only; take a backup before switching; no automatic drop |
| Shared DB credential exposure | Least-privilege account, environment-only storage, rotation by the owner (CD-03) |

**Rollback:** the control plane can be redeployed with the previous build against the backed-up development database. Tenant databases are untouched. The bootstrap mode change is additive: the previous callers send no body, which means SEEDED (§6.4).
